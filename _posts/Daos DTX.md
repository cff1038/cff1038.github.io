# **Intel Daos DTX 原理分析**

---

## 1\. DAOS DTX 技术背景

DAOS（Distributed Asynchronous Object Storage）是 Intel 推出的面向 HPC、AI 训练、超算场景的**高性能异步分布式对象存储**，主打无中心架构、NVMe 全闪存、异步 IO、分片对象存储模型。相较于传统分布式存储（Ceph、Lustre），DAOS 放弃了重型一致性协议，优先追求吞吐、延迟、大规模并发能力，但也因此引入了分布式数据一致性的新挑战，DTX 机制正是为解决该痛点而生。

在 DAOS 原生架构中，业务数据会按照 Pool、Container、Target 三级架构打散存储，单次业务写入、对象修改、元数据更新往往会横跨多个服务 Target、多个存储节点。在无事务机制的情况下，网络抖动、节点离线、并发覆盖、IO 中断都会导致**多副本/多分片写入状态不一致**：部分 Target 写入成功、部分失败，出现数据残留、元数据断层、孤儿对象、版本错乱等问题。

传统数据库 2PC/3PC 事务协议开销大、交互多、锁粒度粗，无法适配 DAOS 高吞吐、低延迟、超大规模并行 IO 的场景；而纯最终一致性模型又无法满足 HPC 任务、AI 检查点、批量数据写入的**强一致原子写入诉求**。

为此，DAOS 自研了 **DTX（Distributed Transaction）轻量化分布式事务子系统**。DTX 不追求通用数据库事务能力，而是**专为存储 IO 场景裁剪优化**：以极简日志、最小网络交互、乐观并发控制实现跨节点、跨分片的原子写入、原子回滚与冲突处理，在几乎不损耗吞吐性能的前提下，补齐 DAOS 分布式数据一致性短板，成为 DAOS 高可靠运行的核心底层机制。

## 2\. 什么是分布式事务

分布式事务是指**跨越多个物理节点、多个存储分片、多个服务实例**的一组读写操作，被封装为一个逻辑不可分割的执行单元。其核心目标是保证分布式环境下，一组关联操作满足数据库 ACID 四大事务特性，解决分布式系统天然存在的网络不可靠、节点故障、并发竞争带来的数据不一致问题。

单机事务可依赖本地日志、文件锁、内存状态实现一致性；但分布式集群中，数据分散、独立服务无全局锁、网络存在分区与延迟，单机事务模型完全失效，必须依赖专门的分布式事务协议保障数据可靠。

### 2\.1 事务 ACID 核心定义

- **原子性（Atomicity）**：事务整体要么全部成功落地，要么全部回滚清零，不存在“半成功”状态。

- **一致性（Consistency）**：事务执行前后，集群数据约束、元数据映射、对象状态始终合法有效。

- **隔离性（Isolation）**：并发事务互相隔离，避免脏写、覆盖、错乱等并发问题。

- **持久性（Durability）**：事务提交成功后数据永久落地，重启、扩容、故障恢复后数据不丢失。

## 3\. Daos DTX 提供的分布式事务特性和使用范围

### 3\.1 核心特性

- **跨 Target 原子提交**：支持一次事务覆盖多个存储分片、多节点对象写入与元数据更新，保证多分片状态统一。

- **轻量化改良 2PC**：删减传统 2PC 阻塞等待、重复握手逻辑，采用异步预提交\+批量确认，极低性能开销。

- **乐观并发控制无排他锁**：基于对象版本号校验实现隔离，不阻塞吞吐，适配高并发 IO。

- **故障自动自愈恢复**：节点重启后自动扫描 DTX 日志，完成未决事务提交或回滚。

- **数据与元数据双一致性**：同时保证业务数据、对象索引、分片映射、版本信息一致性。

- **事务冲突检测与仲裁**：内置对象版本冲突、写覆盖冲突检测机制，解决并发事务竞争问题。

### 3\.2 适用范围

DTX 主要服务于 DAOS 关键一致性写入场景：跨分片批量对象读写、容器迁移、分片重构、快照打点、检查点写入、副本同步、元数据批量更新。不适用长事务、高频极小事务、跨集群复杂业务事务。

## 4\. Daos DTX 原理分析（含代码细节、成功流程、冲突处理）

DAOS DTX 整体架构核心为：**全局 DTXID 串联多节点状态 \+ 本地持久化事务日志 \+ 改良异步 2PC 流程 \+ 版本号乐观冲突检测 \+ 后台恢复巡检**。区别于通用事务，DTX 所有逻辑深度耦合 DAOS 对象 IO 流程，代码层面完全嵌入底层 I/O 栈。

### 4\.1 DTX 核心数据结构（代码原理细节）

DAOS 内核源码中，每一次分布式事务都会初始化一个 `dtx_handle` 事务句柄，核心字段如下（开源源码逻辑精简）：

```c
// DTX 事务核心句柄结构（源码抽象）
struct dtx_handle {
    uint64_t  dtx_id;        // 全局唯一事务ID
    uint32_t  dtx_state;     // 事务状态：INIT/PREPARE/COMMIT/ABORT
    uint32_t  dtx_flags;     // 事务属性：只读/批量/跨分片/可恢复
    daos_obj_ver_t dtx_ver;  // 本次事务绑定的对象版本号
    uint32_t  target_cnt;    // 参与事务的Target数量
    struct dtx_target_info *targets; // 所有参与节点状态
};

```

**关键原理**：

- `dtx_id` 全局唯一，多节点通过该 ID 统一事务状态，避免事务混乱。

- `dtx_state` 是 2PC 流转的核心状态机，严格控制事务分步执行。

- `dtx_ver` 版本号是**冲突检测的核心依据**，用于判断并发写覆盖。

### 4\.2 事务成功完整流转流程（代码级时序）

一次标准 DTX 成功事务分为：初始化 → 预提交（Prepare）→ 落地日志 → 正式提交（Commit）→ 状态清理，完全贴合改良版异步 2PC。

#### 4\.2\.1 阶段1：事务初始化（客户端 \& 服务端）

客户端发起跨分片写入时，首先调用 `dc_dtx_create()` 生成全局 DTXID，扫描本次 IO 涉及的所有 Target 分片，构建事务节点列表。服务端每个 Target 接收事务请求后，创建本地 `dtx_handle`，标记状态为 `DTX_STATE_INIT`，绑定当前对象最新版本号，禁止脏覆盖。

- `dtx_id`：全局唯一，多节点依靠该 ID 统一事务状态。
- `dtx_state`：状态机，驱动 2PC 流转。
- `dtx_ver`：版本号，作为乐观并发冲突检测核心依据。

> 
> 每个 DAOS Target 本地维护两棵独立 B‑Tree，以`dtx_id`作为索引 key：
> 
> 
> 1. **Active DTX Tree（活跃事务树）**
> 2. **Committed DTX Tree（已提交事务树）**

### 4.2 Active DTX Tree 与 Committed DTX Tree 原理

#### 4.2.1 Active DTX Tree（活跃事务树）

Active DTX Tree 保存**所有未完成、处于进行中的事务**，包括状态为 `INIT`、`PREPARED` 的事务。

- 存储内容：dtx_id、事务状态、参与对象、对象版本号、事务日志指针、参与的 replicas/target 信息。
- 主要作用：
  1. **快速查找未决事务**：发生 IO 访问、并发写冲突、节点恢复时，通过 dtx_id 快速检索当前 Target 上正在进行的事务。
  2. **辅助冲突检测**：新事务预提交阶段，查询 Active 树，判断目标对象是否被其他活跃事务修改，配合版本号完成冲突判定。
  3. **故障恢复扫描**：节点重启后，后台`dtx_recovery_thread`遍历 Active DTX Tree；对`PREPARED`尝试补提交，对`INIT`执行回滚。
  4. **事务状态更新载体**：事务执行 Prepare 后条目驻留 Active 树；未完成提交前不会移出。

> 
> 关键：只要事务尚未完成最终提交确认，条目就保留在 Active DTX Tree。

#### 4.2.2 Committed DTX Tree（已提交事务树）

当事务完成完整 2PC 流程、状态置为`DTX_STATE_COMMITTED`，事务条目从 Active DTX Tree 移除，插入 Committed DTX Tree。

- 存储内容：dtx_id、提交时间戳、参与对象、版本信息、日志持久化记录。
- 主要作用：
  1. **幂等校验**：客户端重复发送 Commit 请求时查询该树，判断 dtx_id 是否已提交，避免重复提交引发重复写入，是分布式事务幂等性的关键保障。
  2. **副本与迁移状态追溯**：副本同步、分片迁移、快照创建时校验事务提交状态，保证多副本之间状态一致。
  3. **后台垃圾回收 GC**：DTX‑GC 线程扫描该树，依据老化时间、引用计数清理过期条目，释放内存与持久化日志资源。
- 生命周期：事务提交后进入 Committed 树；直到 GC 判定不再需要追溯，才会删除条目。

#### 4.2.3 双树完整流转时序

```
事务创建 → 插入 Active DTX Tree
全部Target Prepare成功 → 收到Commit指令 → 事务提交成功
→ 从Active DTX Tree删除条目 → 插入Committed DTX Tree
→ GC后台定时扫描，过期后从Committed DTX Tree删除

事务中途Abort → 直接从Active DTX Tree删除，不进入Committed树
```

简化源码伪代码：

```
// 事务提交完成后，双树状态切换
int dtx_move_active_to_committed(struct dtx_handle *dtx)
{
    // 1.从Active DTX Tree删除该dtx_id
    dtx_tree_delete(&dtx->target->dtx_active_tree, dtx->dtx_id);
    // 2.将事务信息插入Committed DTX Tree
    dtx_tree_insert(&dtx->target->dtx_committed_tree, dtx->dtx_id, dtx);
    return 0;
}
```

### 4.3 事务成功完整流转流程（结合双树）

1. **阶段 1：事务初始化**
客户端调用`dc_dtx_create()`生成全局 DTXID，识别本次 IO 涉及的全部 Target 分片。服务端 Target 创建`dtx_handle`，状态置`INIT`，**插入 Active DTX Tree**。
2. **阶段 2：预提交 Prepare**
执行`dtx_prepare()`：将业务数据、元数据写入临时事务缓冲区，持久化 DTX 事务日志，事务状态更新为`PREPARED`，条目仍然保存在 Active DTX Tree。
任意 Target 返回失败 → 执行`dtx_abort()`，清理缓冲区临时数据，**从 Active DTX Tree 删除该事务条目**，事务终止。
3. **阶段 3：正式提交 Commit**
客户端收集全部 Target Prepare 成功应答后，下发全局 Commit 请求。
服务端执行`dtx_commit()`：临时缓冲区数据转正，更新对象版本号与元数据索引；事务状态变更为`DTX_STATE_COMMITTED`。

> 
> 核心动作：**将该 dtx 条目从 Active DTX Tree 迁移到 Committed DTX Tree**。

4. **阶段 4：事务收尾与 GC**
业务可以正常读取已提交的最新数据。后台 GC 线程定期遍历 Committed DTX Tree，清理老化的事务条目，释放内存与磁盘日志资源。

### 4.4 DTX 事务冲突检测与处理机制

DAOS 采用乐观并发控制，依靠对象版本号比对 + Active DTX Tree 检索实现冲突检测。

#### 4.4.1 冲突产生场景

两个并发事务同时修改同一个对象、同一个分片；后发起的事务在 Prepare 阶段检测版本不匹配，触发事务冲突。

#### 4.4.2 冲突检测逻辑（伪代码）

```
// DTX 冲突检测核心逻辑
if (local_obj_version != dtx->dtx_ver) {
    // 查询Active DTX Tree，确认对象上是否存在活跃修改事务
    if (dtx_tree_find(&target->dtx_active_tree, dtx->dtx_id)) {
        dtx_abort(dtx);
        return -DER_TX_CONFLICT;
    }
}
```

> 
> 两层判定：对象版本号校验 + 查询 Active DTX Tree 确认活跃事务，避免漏判并发修改。

#### 4.4.3 冲突处理策略

1. **即时本地回滚**：冲突事务执行 abort，清空全部临时写入，从 Active DTX Tree 移除，不会产生脏数据。
2. **客户端有限重试**：客户端捕获`DER_TX_CONFLICT`错误，重新拉取对象最新版本号，新建事务进行重试。
3. **不阻塞全局 IO**：仅冲突事务失败回滚，其余正常 IO 不受影响，保障集群整体吞吐。

### 4.5 故障恢复原理（结合双树）

节点重启完成后，后台线程`dtx_recovery_thread`启动，**遍历 Active DTX Tree**：

- 条目状态为`PREPARED`：预提交已完成，自动执行补提交；提交成功后迁移至 Committed DTX Tree。
- 条目状态为`INIT`：事务未完成预提交，自动执行 abort，直接从 Active 树删除。

Committed DTX Tree 承担幂等防护：恢复过程如果收到重复 Commit 请求，查询 Committed 树，发现 dtx_id 已经提交，则直接返回成功，防止重复写入。

#### 4\.2\.2 阶段2：预提交 Prepare（核心原子保障）

服务端执行 `dtx_prepare()` 逻辑：

- 将用户数据、对象元数据、索引信息**写入临时事务缓冲区**；

- 落地轻量化 DTX 持久化日志（记录 dtx\_id、状态、版本、操作对象）；

- 不对外更新正式数据视图，业务无感知；

- 所有参与 Target 全部 Prepare 成功后，返回 OK 给客户端。

**设计关键点**：只要任意一台 Target 预提交失败，全局直接触发 `dtx_abort()`，清空所有缓冲区，事务归零，保证原子性。

#### 4\.2\.3 阶段3：正式提交 Commit

客户端收集所有节点 Prepare 成功应答后，发起全局 Commit 请求，服务端执行 `dtx_commit()`：

- 将临时缓冲区数据刷入正式对象存储；

- 更新对象全局版本号、元数据索引；

- 事务状态变更为 `DTX_STATE_COMMITTED`；

- 对外暴露最新数据视图，业务读取生效。

#### 4\.2\.4 阶段4：事务收尾

全部节点提交完成后，批量清理过期事务缓存，异步回收 DTX 句柄，保留持久化日志用于故障回溯。

### 4\.3 DTX 事务冲突检测与处理机制（核心难点）

DAOS 采用**乐观并发控制**，无锁并发，冲突全部依靠**对象版本号比对**实现，是 DTX 隔离性的核心。

#### 4\.3\.1 冲突产生场景

两个并发事务同时修改**同一个对象、同一个分片**，后发起的事务会检测到版本不匹配，触发事务冲突。

#### 4\.3\.2 冲突检测代码逻辑（原理示例）

在 `dtx_prepare()` 阶段，DAOS 会强制校验版本，伪代码逻辑如下：

```c
// DTX 冲突检测核心逻辑
if (local_obj_version != dtx->dtx_ver) {
    // 当前对象版本已被其他事务修改，存在写冲突
    dtx_abort(dtx);       // 本地立即回滚
    return -DER_TX_CONFLICT; // 返回事务冲突错误
}

```

原理：事务初始化时绑定一个「起始版本号」，预提交阶段如果发现真实对象版本已经变更，说明被并发事务修改，直接判定冲突。

#### 4\.3\.3 冲突处理策略

- **即时回滚**：冲突事务立刻 abort，清空所有临时写入，不会产生脏数据。

- **客户端重试机制**：DAOS 客户端捕获`DER_TX_CONFLICT` 错误后，自动进行有限次重试，重新获取最新版本、新建事务。

- **避免写覆盖**：保证后发起的事务不会覆盖已提交的并发写入，彻底解决脏写问题。

- **无锁高性能**：全程不阻塞全局 IO，仅冲突事务失败，不影响集群整体吞吐。

### 4\.4 故障恢复原理（宕机/断网事务处理）

节点重启后，DTX 后台线程 `dtx_recovery_thread` 扫描本地持久化日志：

- 处于 **PREPARED** 状态：说明预提交成功，自动补提交，保证数据落地；

- 处于 **INIT** 状态：说明事务未完成，自动全局回滚；

- 清理陈旧超时事务，防止内存泄漏与状态悬挂。

## 5\. 为什么需要 DTX 这种事务设计

### 5\.1 解决分布式分片存储的一致性硬伤

DAOS 多 Target 分片架构天然存在多节点写入状态不一致风险，普通 IO 模型无法保证跨节点原子性，DTX 是唯一能在高性能前提下保证多分片写入原子性的底层机制。

### 5\.2 兼顾 HPC 高性能与一致性的平衡

传统 2PC/数据库事务延迟高、交互重、锁竞争强，完全不适合超算并行 IO。DTX 轻量化状态机、异步流程、无锁乐观并发，几乎无损性能，是存储场景专属的事务模型。

### 5\.3 依靠版本冲突机制解决并发写竞争

大规模并行计算场景下，多进程并发写同一个对象是常态。DTX 版本校验\+自动重试机制，既保证并发吞吐，又杜绝数据覆盖错乱，适配 AI、超算核心业务。

### 5\.4 实现故障自愈，降低大规模集群运维成本

大规模集群故障常态化，DTX 自动恢复、自动回滚能力，避免人工介入修复数据，极大提升 DAOS 集群可用性与稳定性。

### 5\.5 原生架构适配，无中间件开销

DTX 深度内嵌 DAOS IO 栈，而非外挂事务组件，贴合对象存储模型、分片机制、异步读写模型，通用性事务方案无法替代。
